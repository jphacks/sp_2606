# 任意MFAとメールによる端末紛失復旧

2026-10-18。実装途中の記録。公開・本番動作確認済みの宣言ではない。

## 決定した仕様

- 任意の認証アプリ(TOTP)方式。SMS・固定の使い捨てバックアップコードは採用しない。
- 初期登録: 現在パスワード確認→QR/手動セットアップキー→6桁コード成功で有効化。
- 次回の新規ログイン: メール・パスワード→認証アプリ。既存ログイン状態が続く間は再入力しない。
- API/BFFとDB関数でMFA確認前のアプリデータ取得・変更を拒否。
- 解除: 現在パスワード＋対象の認証アプリのコード。解除後ログアウト。
- 紛失: メール・パスワードでログイン→登録メールへの6桁復旧コード→新しいQR/キーで再登録→利用再開。
- 復旧コードは10分、有効なチャレンジへの入力は5回。再送60秒待機、利用者ごと1分1回・1日5回。再送時に古いチャレンジは失効。
- メール宛先はAuthの検証済みアカウント情報に固定。リクエストJSONに任意宛先・ユーザーIDを受け付けない。
- 復旧コードは暗号学的乱数。DBには利用者ID・リクエストIDを含むサーバー秘密鍵のHMACのみ保存。コードはCookieやログに保存しない。
- チャレンジIDは暗号化HttpOnly/Secure/SameSite Cookieでブラウザと結び付ける。
- 成功時にDBを先に閉鎖状態にし、旧因子をAuth管理APIで削除、全端末のセッションを失効、新しい限定セッションで再登録を許可する。
- JWTが期限内でも、復旧前に発行された古いJWTはDB側で拒否。登録を終えるまで認証因子の削除だけではアクセスを許可しない。
- 復旧後は新しい認証アプリの登録を必須にする。登録完了をメール通知する。通知失敗は完了とは分けて扱い、成功通知を偽装しない。
- メールアカウントを復旧の信頼先とする。メール乗っ取りに対して独立した防御にはならない点を合意済み。
- パスワードも不明なら、まず既存のパスワード再設定メールを使う。パスワードの再設定でMFAを解除しない。

## サーバー専用設定（未登録）

`.env.example`の下記項目を、ローカルでは`.env.local`、公開時はVercelのServer用環境変数に設定する。チャット、Git、NEXT_PUBLIC_へは出さない。

- `SUPABASE_RECOVERY_SECRET_KEY`: Supabaseのサーバー専用Secretキー。復旧API内のAuth管理操作と、管理者専用の限定RPCだけで使用。通常の投稿・DM・プロフィールには利用しない。
- `RECOVERY_SMTP_HOST` / `RECOVERY_SMTP_PORT`: 専用Gmailならsmtp.gmail.com / 465。
- `RECOVERY_SMTP_USER` / `RECOVERY_MAIL_FROM`: アプリ専用の送信用メールアドレス。
- `RECOVERY_SMTP_PASSWORD`: 専用Gmailのアプリパスワード。Googleの通常ログインパスワードではない。

既存のSupabase側SMTP設定は変更しない。アプリからの復旧コード・完了通知用に同じ専用送信元を利用する想定。
SupabaseのSecretキーは権限が大きい。`src/lib/mfa-recovery-server.ts`はserver-onlyとし、復旧API以外には持ち込まない。

## メール復旧後の任意再登録（SQL23）

- 新しい端末がなくてもメール・パスワードで利用再開できるよう変更。
- 旧因子の削除・全セッション失効・復旧コードの検証と消費は継続。
- 削除前の中間状態ではアプリデータを開かない。管理者専用の完了関数が、消費済みの同じ復旧リクエスト・期限・因子の削除を確認した後にだけ解除する。
- 古いJWTの拒否は解除後も継続。設定からMFAを再登録した場合は再びaal2を要求する。
- 復旧完了メールは「復旧完了・二要素認証オフ」と案内し、再登録完了の通知とは区別。
- DBのSQL23が未適用なら復旧を開始/消費せず503を返す。旧公開コードで開始した再登録待ち状態は移行時に一括解除しない。
