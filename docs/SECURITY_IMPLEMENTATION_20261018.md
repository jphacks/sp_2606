- 文書の性質：現行実装の仕様・検証状況・残課題の整理。安全性保証、認証取得、第三者監査報告ではない。

## 1. 目的と旧文書との関係

DM、限定公開の文章、認証情報を保護し、学習記録・交流を意図した範囲で共有する。無料運用を目標にするが、費用ゼロや無制限の利用を保証しない。

旧 `docs/security-requirements.md` と基本方針は要求の原典として保持する。本書はそれらを削除・達成扱いにせず、会話で変更した仕様と現行コードを整理する。特に次は旧文書と区別する。

| 項目 | 現行仕様 |
|---|---|
| 文章の限定公開 | 相互フォローではなく、承認済みフォロワーのみ |
| 公開範囲の設定場所 | メール確認後のプロフィール・設定。登録フォームでは選ばない |
| 学習メモ | 任意入力。共有対象のメモは文章の共通公開設定に従う |
| MFAメール復旧後 | 二要素認証をオフにして利用再開。新端末での再登録は任意 |
| 通報 | 今回は見送り。実装済みとしない |
| 招待制 | チーム内試用の運用方針。招待コード・許可リストによる登録制限は未実装 |

旧文書の全項目を本書だけで網羅・達成判定したものではない。未記載の原要件を不要と扱わない。

## 2. 状態・優先度の定義

- **実装済み**：コードに処理が存在する。本番の全条件で検証済みとは限らない。
- **検証記録あり**：記載した環境・条件で確認した記録がある。自動テスト、実サービス、本人報告を区別する。
- **未確認**：証拠不足、または本番条件での追加試験が必要。
- **未実装／運用未整備**：今後の課題。公開済みであっても達成扱いにしない。

P0 MUST：認証・認可・秘密保護の基本条件。失敗時は影響機能の公開を止める。P1 MUST：一般公開を広げる前に整備・検証する条件。P2 SHOULD：継続的な改善。現時点の公開は全ゲート合格を意味しない。

## 3. 保護対象と信頼境界

| 対象 | 取扱い |
|---|---|
| DM本文 | 会話当事者に限定。E2EE未実装。権限を奪われたサーバー・DBで読まれる可能性あり |
| 投稿本文・共有対象メモ | 文章のアカウント共通公開設定に従う |
| 基本プロフィール・学習分野・日付・時間 | 原則ログイン済み利用者向け。ブロック・停止などの制限を適用 |
| 大学・学部・業務・都道府県等の属性 | 入力されたものはログイン済み全員に公開。所属等は任意。再識別の可能性あり |
| パスワード | Supabase Authで管理・検証。独自プロフィールテーブルに平文保存しない |
| アクセス／更新トークン | 暗号化したアプリCookie内で扱う。秘密情報として保護 |
| 管理キー・SMTP認証情報・セッション暗号鍵 | サーバー専用設定。公開コード・ブラウザ・通知へ含めない |
| セキュリティ監視集計 | 処理種別・時間帯・結果別件数のみ。個人情報・秘密・本文を含めない |

ブラウザ入力を信用しない。ブラウザ→Next.js→Supabaseの各境界で確認する。Supabase公開用キーは公開前提の識別情報であり、管理用Secretと区別する。

## 4. 認証・セッション

| ID | 優先度 | 現行の要件・実装 | 状態・根拠 |
|---|---|---|---|
| AUTH-01 | P0 MUST | メール・パスワード認証をSupabase Authで行う。登録時は12〜128文字をサーバー検証 | 実装済み：`src/lib/validation.ts`、認証API |
| AUTH-02 | P0 MUST | 登録・確認・再設定の入口を除き、アプリデータは認証確認後に返す | 実装済み。匿名HTTP拒否試験の記録あり |
| AUTH-03 | P0 MUST | 通常のパスワード変更は現在パスワードを再検証。メール再設定は専用の短期許可を要求 | 実装済み。許可の期限・アカウント等の自動試験あり。本番の全変更経路は追加確認 |
| SES-01 | P0 MUST | セッションのaccess/refresh token、期限、作成・最終確認日時、user IDをAES-256-GCMで暗号化 | 実装済み：`server.ts`、`session-crypto.ts` |
| SES-02 | P0 MUST | HttpOnly、SameSite=Lax、Path=/。productionはSecure・`__Host-` Cookie | 実装済み。開発HTTPと本番HTTPSを区別 |
| SES-03 | P0 MUST | 作成から7日、最終確認から1日を超えるセッションを拒否。更新しても元の作成日時を保持 | 実装済み。Cookie期限だけに依存しない |
| SES-04 | P0 MUST | ログアウトでアプリCookie・復旧許可を破棄 | 実装済み。盗まれた全トークンの即時失効保証とは別 |

HttpOnlyはJavaScriptによる直接読取を制限するが、XSS経由の操作や盗まれたCookieの再利用を全面的に防ぐものではない。セッション暗号鍵交換だけでは、Supabase側の既存トークンを失効できない。

## 5. 任意の二要素認証・メール復旧

| ID | 優先度 | 現行の要件・実装 | 状態 |
|---|---|---|---|
| MFA-01 | P0 MUST | 任意TOTP。現在パスワード確認後、QR／手動キーを提示し、6桁コード検証成功で有効化 | 実装済み。本人の登録・再ログイン成功報告あり |
| MFA-02 | P0 MUST | MFA利用者は追加認証前のアプリデータ取得・更新をAPIとDBで拒否 | 実装済み。隔離DB・HTTP試験あり |
| MFA-03 | P0 MUST | 解除は現在パスワードと認証アプリコードで確認 | 実装済み。実サービスの全分岐は追加確認 |
| REC-01 | P0 MUST | 紛失復旧はパスワード再確認＋Authから得た登録済みメール宛てのコード。任意宛先・任意user IDを信用しない | 実装済み |
| REC-02 | P0 MUST | 乱数6桁、10分、チャレンジ当たり5回。再送60秒、ユーザーごと1日5回。再送で旧チャレンジ失効 | 実装済み。メールサービス全体の上限とは別 |
| REC-03 | P0 MUST | DBには利用者・要求IDに結び付けたHMACを保存。生コードをCookie・ログに保存しない | 実装済み |
| REC-04 | P0 MUST | 復旧Cookieを暗号化しブラウザと結び付ける。消費・中間状態・完了状態をDBで管理 | 実装済み |
| REC-05 | P0 MUST | 旧認証因子を削除し、全セッション失効処理を行う。古いJWTのアプリDBアクセスも拒否 | 実装済み。実端末・実トークンでの網羅試験は追加確認 |
| REC-06 | P0 MUST | 復旧後はMFAオフで再開可能。再登録任意。完了メールは「復旧完了・MFAオフ」と区別して案内 | SQL23を含む実装・反映記録あり |

メールを復旧の信頼先とするため、メールアカウント侵害に独立した防御ではない。メールサービス側のMFAを必須設定済みとは仮定しない。実メールの到着・タイムライン復帰の本人報告はあるが、旧JWT拒否や障害分岐を含む本番全工程の網羅確認とは区別する。

## 6. 認可・DB権限

| ID | 優先度 | 要件・実装 |
|---|---|---|
| DB-01 | P0 MUST | アプリ対象テーブルのRLSを有効化し、anon/authenticatedの直接アクセス権限を制限 |
| DB-02 | P0 MUST | 公開RPCは必要なもののみ実行許可。関数内でAuth ID・停止・公開範囲等を確認 |
| DB-03 | P0 MUST | SECURITY DEFINER関数は所有者権限で動くことを前提に、実行GRANT・入力・認可・search_pathを確認 |
| DB-04 | P0 MUST | 投稿削除は投稿者本人、DM取得は当事者。検索・返信数・フィードからも非公開情報を漏らさない |
| DB-05 | P0 MUST | 文章は「ログイン済み全員／承認済みフォロワー／自分のみ」。フォローバック不要。最新設定を反映 |
| DB-06 | P0 MUST | ブロック・停止を関連操作の許可より優先。ブロック後の過去DMは閲覧可能、新規送信禁止という例外を明記 |
| DB-07 | P0 MUST | DM承認前は送信1件。申請は初回を含め2回。削除後は削除済み表示とする |
| DB-08 | P0 MUST | おすすめにDM・限定公開文章を使わず、学習分野・経験・目標等の登録情報を使う |

上記は実装済み。隔離DBで公開範囲・フォロー承認・第三者DM拒否・ブロック・削除・直接アクセス等の試験記録あり。本番での実ユーザー別JWTを使った横断試験は追加課題。

Storage・View：現行の画像はDB経由のプロフィール画像処理であり、Storageによる投稿画像機能を実装済みとしない。過去の本番監査ではStorageバケット／ポリシー・Viewなしを確認したが、今後追加時には別途RLS・GRANT・所有者権限・公開URL経路を評価する。

|---|---|---|---|

| IMG-01 | P0 MUST | プロフィール画像をSharpでデコード・回転・192×192 JPEG再変換。メタデータ等を引き継がない | 元ファイルをそのまま配信しない |
| IMG-02 | P0 MUST | Base64入力最大65,536文字、デコード画素数2千万、出力最大49,152バイト。JPEG/PNG/WebP/AVIF/HEIFの形式判定 | HEIC/HEIFの全実機・全コーデック対応は未確認。変換不能は拒否 |

入力の主な現行上限：表示名30文字、自己紹介500文字、投稿2,000文字、返信500文字、学習メモ500文字、学習時間1〜1,440分。サーバーとSQL双方の整合を変更時に確認する。

## 8. 操作回数・費用濫用

**P0 MUST：** 書き込み・主要読取はDBのカウンターと許可済みRPCを使い、UIを迂回しても制限を適用する。SQLの時間窓は固定窓であり、滑動窓やユーザー横断の全悪用防止を保証しない。

代表的なコード設定：投稿5回/分・30回/日、フォロー操作10回/分・100回/日、リアクション30回/分・500回/日、プロフィール画像変更5回/分・30回/日。対象は各操作のユーザー別予算。申請回数、受信先・全体予算などの別制限もある。

**未確認／改善：** Supabase Authへの直接要求の本番制限、SMTP配信上限・到達性、同一ネットワークからの一斉登録、分散攻撃・大量登録・費用上限。20人や100人分のダミーデータ表示は、その人数の同時操作の負荷試験ではない。

## 9. 秘密情報・開発・CI

| ID | 優先度 | 要件・実装 |
|---|---|---|
| KEY-01 | P0 MUST | 管理キー・SMTPパスワード・セッション暗号鍵はサーバー環境変数。NEXT_PUBLIC_・ソース・README・Issue・画像へ出さない |
| KEY-02 | P0 MUST | ローカル.env.localをGit・デプロイアップロード対象から除外。Vercel本番に承認済みSecretとして保存 |
| KEY-03 | P0 MUST | 管理クライアントはserver-only。通常の投稿・DMは利用者権限で処理 |
| KEY-04 | P1 MUST | 管理キーの広い権限を認識する。現在は復旧と固定監視RPCに共用。用途別の最小権限分離は未完了 |
| CI-01 | P0 MUST | GitHub Actionsで型チェック・隔離DB等の試験・ビルド・未認証/Origin/CSRF HTTP試験 |
| CI-02 | P1 MUST | CodeQL解析、Dependabotの更新PR、Gitleaksの履歴検査を構成。ActionsはSHA固定 |
| CI-03 | P1 MUST | Gitleaks検知時は失敗、通知に秘密値を含めない。main等はIssue作成、PRは書込権限を与えずチェック失敗 |

GitHub標準Secret Scanning、push protection、Dependabot alertsの管理画面設定、必須チェック付きブランチ保護は管理者確認待ち。ワークフローの存在だけでこれらを有効化済みとしない。

AI/Codex利用のMUST：実キー・パスワード・OTPをプロンプトや公開ログへ貼らない。外部資料を指示権限として扱わない。RLS・認可・CSRF・監視をテストの都合で弱めない。差分とテスト結果を確認し、失敗・未実施を隠さない。AI利用そのものを安全性の根拠にしない。

## 10. 監視・通知

実装・反映記録あり。GitHub定期実行の遅延・停止、通知設定による不達があり得る。

| 対象 | 実行 | 内容 |
|---|---|---|
| Git履歴 | push/PR・週次・手動 | GitleaksとCoStepルール。秘密候補と検査失敗を検知 |
| 公開ファイル | main push・約30分・手動 | トップから発見できる同一オリジンJSを検査。最大100ファイル、各2MB、合計20MB |
| 認証処理 | 約15分・手動 | 直近30分のアプリ経由ログイン・MFA・再設定・復旧の集計を判定 |
| 通知 | 異常／取得不能時 | リポジトリのIssueに作成・追記、ryo7-7へ担当割当。メールはGitHub通知設定次第 |

直近30分の暫定しきい値：ログイン拒否30件以上かつ拒否率70%以上、MFA拒否20件以上、再設定要求15件以上、MFA復旧要求15件以上、関連サーバーエラー5件以上。

監視集計にはIP・user ID・メール・本文・秘密値を保存しない。古い集計は次の記録時に7日以前を削除。監視APIはGitHub OIDCの署名・issuer・audience・期限・repo/owner数値ID・main・専用ワークフロー・実行イベントを確認し、集計のみ返す。GitHubへ本番DBキーを渡さない。

検知不能範囲：Supabaseへの直接アクセス、未使用の盗難キー、全ログ・メモリ・過去デプロイ・未発見チャンク・未知の秘密形式。監視は侵入や漏洩の確定判定ではない。

## 11. インシデント対応

**実装済み：** `COSTEP_INCIDENT_MODE`のnone/recovery/all。無効値はall扱い。recoveryはMFAメール復旧停止、allはページ/API等を503/no-storeで返し、アクセスしたブラウザの関連Cookieを削除。静的JSは配信継続。

**実装済み：** `SESSION_NOT_BEFORE`で古い作成日時のアプリセッション拒否。セッション暗号鍵交換も可能。

**運営が実行すること：**

1. 検出結果を確認。本物の秘密キーが公開されていたら、悪用の証拠を待たず対応する（公開前提のキーとの区別が必要）。
2. 必要な機能／全体を停止し再デプロイする。
3. 発行元で漏れた管理キー・SMTPアプリパスワードを失効し、新規発行・本番設定更新する。
4. 必要に応じSupabaseセッション・トークンにも対応。古いデプロイを含め影響調査する。
5. 新旧キー・ログイン・メール等を秘密値を残さず確認し、連絡・記録・再開を判断する。

アプリ停止はSupabaseの直接アクセスを止めない。セッション暗号鍵交換は盗まれたSupabaseトークンを直接失効しない。自動鍵交換・自動停止は未実装。実キーの失効・停止再開の本番訓練は未実施。
