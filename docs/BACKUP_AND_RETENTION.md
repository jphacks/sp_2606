# バックアップ・復元・保持期限

更新：2026-10-19。ユーザー承認済みの保持方針を実装した。以下の「確認済み」は明記した範囲に限る。

## データ別の扱い

| データ | 保持・削除 |
|---|---|
| 通常DBのアカウント・プロフィール・投稿・返信・学習記録・DM等 | 退会時にAuthのハード削除と外部キーの連鎖で削除 |
| 退会済みIDと退会日時 | 運営専用の `private.account_deletions` に8日。本文・メールは記録しない。復元時の再削除に使う |
| 削除前の暗号化バックアップ | 取得開始から7日で復元ツールが利用を拒否。Macの次回整理処理でファイル削除 |
| 個人識別情報を含めない認証監視集計 | 7日より古い行を整理 |
| Supabase/Vercel/Gmail/GitHub等のサービス側ログ・送信済みメール | 各提供元の保持条件に従う。この7日・8日設定で一括消去されるものではない |
| 他人が保存した画像・画面コピー | このアプリからの削除はできない |

8日の退会記録は、最大7日のバックアップへ削除済みデータを戻さないための例外として合意済み。SQLの取得関数は8日超の記録を返さない。物理削除は定期ジョブの実行時となる。通報機能は未採用であり、通報証拠の保持処理は実装していない。

## 実装

- `202610190027_retention.sql`：Auth削除と同じトランザクションのトリガーでID・日時を記録。記録に失敗すると削除自体も失敗する。一般ユーザーにはテーブル権限・関数実行権限を与えない。
- `POST /api/security-monitor/retention`：既存のGitHub Actions OIDC認証でリポジトリ・main・指定ワークフロー等を確認し、固定の整理RPCだけを実行する。管理キーやDB接続情報をGitHubへ追加しない。
- 既存Runtime security monitorは15分間隔で整理を要求する。GitHub側の遅延・停止時は実行されない。失敗は既存監視のIssue通知対象になる。
- `scripts/backup/`：PostgreSQLの論理バックアップをメモリ内でAES-256-GCM暗号化してからディスクへ書く。改ざん・別鍵・期限切れは復元不可。リモート接続はTLS `verify-full` と公式CA証明書を使う。
- `.env.backup.local`、専用鍵 `.backup-key.local`、`.private-backups/` はGitとVercel転送の対象外。設定・鍵・アーカイブは600、保存ディレクトリは700。値やDBエラー本文をログへ出さない。

## 取得範囲

`public`・`private`・`auth` スキーマを取得する。退会記録のデータは古い記録を延命しないため除外し、復元直前・直後に本番から新しい記録を取得する。Authのセッション、refresh token、ワンタイムトークン、認証フロー、MFA照合・WebAuthn照合・SAML中継などの一時データも除外する。復元後は再ログインが必要になる。

Authユーザー・パスワードハッシュ・MFA登録情報も含む機密バックアップである。専用鍵の保護が必要。ACL定義はアーカイブに保存するが、隔離復元テストでは所有者・GRANTを適用しない。Storageオブジェクト実体・外部サービスの設定・暗号鍵・Vercel環境変数はこのDBダンプには含まない。現行画像はDB保存。Storageを採用する際は実体の別バックアップを必須とする。

## 自動取得の運用

このMacの `local.costep.backup` LaunchAgentが、ログイン中に1時間ごとに期限切れ整理を実行し、直近バックアップから24時間以上なら取得する。追加の有料サービスは使わない。

**電源オフ・スリープ・ログアウト中は動かない。** 日次取得の保証や、7日ちょうどでの物理削除の保証はない。期限切れアーカイブは削除前でもツールが復元を拒否するが、鍵を持つ管理者による独自復号を技術的に防ぐ仕組みではない。ファイル削除はSSDの完全消去を保証しない。

```sh
npm run backup:status
npm run backup:create
npm run backup:maintain
npm run backup:prune
```

設定・鍵はチャットやGitHubに貼らない。ログは `.private-backups/maintenance.log` と `maintenance-error.log`。定期処理の終了コード・取得日時は運営が確認する。Macでのバックアップ失敗の外部自動通知は未実装。

## 復元手順と安全条件

1. 別のローカルPostgreSQLに空DBを作る。DB名は `costep_restore_test_` で始める。必要な拡張・Auth用ロールを事前に用意する。
2. `.env.backup.local` の `RESTORE_DATABASE_URL` にそのDBを設定する。接続先はloopback限定。既存テーブルのあるDBは拒否する。
3. `npm run backup:restore-test -- .private-backups/<対象ファイル>.csbk` を実行する。
4. 新しい退会記録を取得できない場合は停止する。復元後にも再取得してAuthから再削除し、外部キーの連鎖を適用する。
5. データ整合・RLS・GRANT・関数所有者・Auth動作・削除再適用を確認する。テスト用DBを削除し、設定の復元先を空に戻す。

本番への切替・上書きコマンドは用意していない。本番復旧にはSupabaseの管理ロール・Auth・拡張・ACL・画像等の整合確認と、切替直前の最新退会記録の再適用が別途必要。一般公開ゲートをこの試験だけで達成扱いにしない。

**残る制約：** 本番が完全に利用不能だと最新の退会記録を取得できず、安全側に停止する。独立した退会記録の退避先は未整備。バックアップと鍵が同じMacにあるため、Mac紛失・故障・侵害に対する別保管と復元保証も未整備。RPO/RTOの保証はしない。
