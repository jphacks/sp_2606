# CoStep セキュリティ想定問答集

作成日：2026年10月18日。発表・審査向け。現在の実装と運用資料に基づく説明であり、安全性の認証や第三者監査の結果ではありません。

## 最初に覚える30秒の説明

> CoStepでは、認証だけでなく「誰がどの情報を見られるか」をサーバーとDBで確認しています。任意の二要素認証、投稿やDMの操作回数制限、秘密情報の混入検査、認証処理の異常監視を組み合わせています。漏洩時に機能を停止し、鍵を交換するための仕組みと手順も用意しました。ただし、すべての攻撃や漏洩を検知できるものではありません。

## 1. 全体・独自性

### Q1. Supabaseを使っているだけではありませんか？
**回答：** 認証の基盤はSupabaseを使っています。その上に、フォロー承認、文章の公開範囲、ブロック、DMの受信条件を確認するDB処理を実装しています。二要素認証のメール復旧、公開ファイルの秘密情報検査、認証処理の件数監視も組み合わせています。

**補足：** 新しい暗号方式を独自に作った、という意味の独自技術ではありません。CoStepの共有ルールをサービス間で矛盾なく適用する実装です。

### Q2. なぜ学習SNSでそこまで対策するのですか？
**回答：** DMや限定公開の文章があり、大学・業務などのプロフィールも扱うためです。利用者が意図した相手にだけ情報が届くことを重視しています。

### Q3. 一番工夫した点は？
**回答：** 画面で隠すだけでなく、DB側でも閲覧条件を確認する点です。また、監視のためにメールアドレスや投稿本文を集めず、認証の成功・拒否・エラーの件数だけを使っています。

## 2. 認証・パスワード

### Q4. パスワードを平文で保存していますか？
**回答：** パスワードの管理・検証はSupabase Authに任せています。CoStep独自のプロフィールテーブルに平文パスワードを保存する構成にはしていません。

**補足：** ログイン時にはパスワードを認証処理へ渡します。「ハッシュ化しているので通信時もパスワードを扱わない」という説明はしません。

### Q5. 通信中にパスワードやDMは見られませんか？
**回答：** 公開サイトとの通信はHTTPSで保護します。ただし、処理を行うサーバーや認証サービスは必要なデータを扱います。DMのエンドツーエンド暗号化は実装していません。

### Q6. 二要素認証はどのような方式ですか？
**回答：** 希望する利用者が認証アプリを登録する方式です。パスワードに加えて、認証アプリの確認コードで本人確認します。利用者全員への強制ではありません。

### Q7. 認証アプリを入れたスマホをなくしたら？
**回答：** パスワードの再確認と、登録メールへ送る復旧コードで復旧できる仕組みを用意しています。コードの有効期限や試行回数も制限します。新しいスマホでは、設定から新しい認証アプリを登録できます。

**補足：** 復旧後の認証アプリ再登録は必須ではない構成です。「再登録しないと利用再開できない」とは説明しません。

### Q8. メールも乗っ取られた場合は安全ですか？
**回答：** メール復旧を用意する以上、メールアカウントの乗っ取りは残るリスクです。メールサービス側の二要素認証を勧めますが、全員が設定しているとは仮定していません。

### Q9. ログイン状態はどう保護していますか？
**回答：** アプリのセッション情報をAES-256-GCMで暗号化し、HttpOnlyなどを設定したCookieで扱います。公開環境ではSecure属性も使い、ブラウザのJavaScriptからCookieの中身を直接読めないようにします。

**補足：** HttpOnlyだけでXSSの被害をすべて防げるわけではありません。

## 3. 公開範囲・アクセス制御

### Q10. 他人のDMをURLやAPIの操作で読めませんか？
**回答：** 会話の当事者かをサーバーとDB処理で確認します。画面にリンクを出さないだけの制御にはしていません。

### Q11. DBへの直接アクセスにはどう対処していますか？
**回答：** テーブルのRLSと権限設定を使い、一般利用者によるテーブルの直接操作を制限します。公開するDB関数でも、本人確認・公開範囲・フォロー承認・ブロックなどを確認します。

**補足：** RLSを有効にしただけで完了ではありません。関数の実行権限や、管理権限で動く関数の中身も確認対象です。管理キーはRLSを迂回できるため、別途保護が必要です。

### Q12. 「フォロワーのみ」は相互フォローが必要ですか？
**回答：** 承認済みのフォロワーが対象で、フォローバックは不要です。ブロックなどの制限は公開設定より優先します。DMの受信条件とは別の設定です。

### Q13. 学習記録は全部非公開にできますか？
**回答：** 文章と学習時間では公開ルールが異なります。基本プロフィールと学習分野・日付・時間は原則ログイン済み利用者に表示し、投稿本文と共有対象の学習メモには文章の共通公開設定を適用します。

**補足：** 「全データが自分だけに設定できる」とは説明しません。

### Q14. おすすめにDMや非公開の文章を使いますか？
**回答：** 使いません。登録された学習分野、技術の習熟度、資格の累計学習時間、目標などから近さを計算します。

## 4. Webアプリへの攻撃・悪用

### Q15. 不正なサイトから勝手に投稿されませんか？
**回答：** 投稿や設定変更などの処理では、送信元の確認やCSRF対策を行います。ログイン済みのブラウザを、不正なサイトから勝手に操作されるリスクを抑えるためです。

**補足：** これはCSRFへの対策であり、不正アクセス全般をこれだけで防ぐという意味ではありません。

### Q16. XSSや不正な入力への対策は？
**回答：** 入力の形式や長さなどをサーバー側で検証し、通常の文字列はReactでテキストとして表示します。CSPなどのレスポンスヘッダーも組み合わせています。

**補足：** 「ReactだからXSSは絶対に起きない」「CSPがあるので安全」とは説明しません。

### Q17. 投稿やDMの連投には対応していますか？
**回答：** 操作回数を制限する処理を用意しています。DB側の投稿・DM処理にも制限を置き、画面のボタンを無効にするだけにはしていません。

**補足：** アプリAPIの制限だけで、Supabase Authへの直接要求や、すべての費用濫用を防げるわけではありません。具体的な数値を聞かれた場合は、最新のSQL・設定で確認して回答します。

### Q18. プロフィール画像はそのまま保存していますか？
**回答：** 切り抜きに加え、サーバー側でサイズ調整・再変換する処理を用意しています。ファイル名の拡張子だけを信用する構成にはしません。

### Q19. PWAだと端末にDMが残りませんか？
**回答：** 認証が必要なデータをオフライン閲覧用に保存する設計にはしていません。サーバーの応答はno-storeとし、通信が必要なデータと、アプリ表示用の静的ファイルを分けて扱います。

**補足：** すでに表示された画面やスクリーンショットを遠隔で消せる、という意味ではありません。

## 5. 秘密情報・監視・漏洩対応

### Q20. 秘密の鍵はどこにありますか？
**回答：** サーバー専用の環境変数で管理し、ブラウザやGitHubのソースコードに含めない構成です。公開前提のSupabaseキーと、管理権限を持つ秘密キーは区別しています。

**補足：** 「管理者以外は技術的に絶対に読めない」ではなく、クラウド側の権限管理とサーバーの保護も必要です。

### Q21. GitHubに秘密が入ったら分かりますか？
**回答：** GitleaksでGit履歴を自動検査し、秘密情報の候補を検知するとチェックを失敗させます。対象の実行では運営担当のGitHub Issueも作成します。未知の形式など、検出できないものはあります。

**補足：** GitHub標準のSecret Scanningやpush protectionが有効になっている、と言い換えてはいけません。標準機能の設定には管理者確認が別途必要です。

### Q22. Webアプリから漏れた場合も検知できますか？
**回答：** 公開トップページと、そこから発見できるJavaScriptの秘密情報候補を検査します。また、アプリを通る認証・復旧処理の件数増加を監視します。ただし、漏洩そのものをすべて検知できるわけではありません。

**補足：** サーバーメモリ、全ログ、過去デプロイ、未発見のJavaScript、Supabaseへの直接アクセス、盗まれたが未使用の鍵などは網羅できません。

### Q23. 監視はリアルタイムですか？
**回答：** 定期監視です。公開ファイルを約30分ごと、認証関連の集計を約15分ごとに確認します。GitHub Actionsの遅延もあり、即時検知や常時監視を保証するものではありません。

### Q24. 監視で個人情報を集めていますか？
**回答：** この監視機能では、処理の種類ごとの成功・拒否・エラー件数を保存します。メールアドレス、IP、ユーザーID、パスワード、確認コード、投稿本文は監視集計に保存しません。

**補足：** クラウドサービスの標準ログまで一切個人情報がないと保証する説明ではありません。件数だけなので、被害者の特定などの詳細調査には別の確認が必要です。

### Q25. 漏洩したら自動で鍵を交換しますか？
**回答：** 自動化しているのは検査・判定・通知までです。誤検知で全利用者を締め出すことを避けるため、停止や鍵の失効・交換は運営が手順に沿って行います。

### Q26. 漏洩した場合、何を削除するのですか？
**回答：** 漏れた秘密キーやメール送信用アプリパスワードを、発行元のサービスで失効させて新しいものに交換します。利用者全員のパスワードを一律に削除する、という意味ではありません。

**補足：** Gitの記述を消すだけでは、コピーされた鍵は使えるままなので不十分です。

### Q27. アプリを停止すれば、漏れた鍵も使えなくなりますか？
**回答：** なりません。アプリ停止とは別に、SupabaseやGoogleなどの発行元で鍵を失効させる必要があります。管理キーによるSupabaseへの直接アクセスは、アプリ停止だけでは止まりません。

### Q28. セッション暗号鍵を交換するとどうなりますか？
**回答：** 古い鍵で作ったアプリのログイン情報を読めなくし、再ログインを求めることができます。ただし、すでに盗まれたSupabaseのトークンを直接失効させる処理とは別です。

### Q29. 監視のために強い管理キーを使っているのは問題では？
**回答：** 現状は、サーバーに保管した既存の復旧用管理キーを、固定された集計処理にも使っています。GitHubにはそのキーを渡さず、署名付きの短命トークンで集計APIだけを読ませています。管理キー自体の権限は広いため、将来は権限をさらに分離する改善余地があります。

## 6. 検証・今後の課題

### Q30. どのように検証しましたか？
**回答：** 型チェック、ビルド、単体・DB権限テスト、匿名アクセスや不正な送信元へのHTTP試験を行っています。GitHub Actionsでもテストや検査を実行しています。

**補足：** 第三者による侵入テストや、本番の鍵を実際に失効させる訓練まで完了したわけではありません。

### Q31. Supabase Security Advisorで問題なしなら安全ですか？
**回答：** 設定上の問題を見つけるための補助として使っています。アプリ独自の公開範囲や復旧処理まで正しいと保証するものではないため、コードや権限の検証も組み合わせます。

### Q32. CodeQLやDependabotは何をしていますか？
**回答：** CodeQLはコード上の問題候補を解析し、Dependabotは依存ライブラリなどの更新PRを作ります。秘密情報の候補検査はGitleaksが担当します。チェックを必ず通さないとマージできない保護設定は、リポジトリ管理者による設定確認が必要です。

### Q33. まだできていない対策はありますか？
**回答：** あります。通報・運営管理、退会処理、バックアップの復元訓練、実際の複数アカウントでの検証拡充などは、一般公開を広げる前の課題です。Supabaseの流出済みパスワード利用防止機能も、現状では有効化していません。

### Q34. 今すぐ一般向けに大規模公開できますか？
**回答：** 現在はハッカソンのプロトタイプとして、チーム内などで検証を進める段階です。一般公開を広げる際は、運営体制や問い合わせ、個人情報の取扱い、復旧・障害対応も整備します。

**補足：** READMEの招待制テストは運用方針であり、招待コードやメール許可リストによる登録制限は未実装です。

## 発表で避けたい表現と置き換え

| 避ける表現 | 実装に合った表現 |
|---|---|
| 乗っ取りを完全に防止 | 乗っ取りのリスクを低減 |
| 秘密は管理者以外に絶対に漏れない | サーバー専用設定と権限管理で保護 |
| 漏洩したパスワードを自動削除 | 漏洩した鍵・送信用認証情報を発行元で失効・交換 |
| 漏洩したら自動で鍵交換 | 自動検査・通知後、運営が失効・交換 |
| Webからの情報漏洩をすべて検知 | 公開ファイルと認証処理の一部の兆候を監視 |
| DBはRLSがあるから安全 | RLS・GRANT・DB関数内の認可を組み合わせる |
| GitHubの標準Secret Scanningを設定済み | Gitleaksによる自動検査を実装済み |
| 招待制なので誰も勝手に登録できない | 現在はチーム内で試用し、登録制限の仕組みは未実装 |
