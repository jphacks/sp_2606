# 退会機能

2026-10-18実装。設定画面からパスワードを再確認し、MFAが有効なら認証アプリの新しい6桁コードも確認する。「退会する」の入力を必須とし、削除中は画面全体を覆って操作を抑止する。

`POST /api/account/delete`：Origin・CSRF・JSON形式・4KiB上限・認証・DB側の敏感操作予算（既存MFA解除予算と共用）を確認する。対象IDは認証済みセッションからのみ取得し、JSONで指定できない。現在パスワードをSupabase Authで再検証し、MFA時は新たな認証セッションでchallengeAndVerifyを行う。

サーバー専用の既存`SUPABASE_RECOVERY_SECRET_KEY`を使い、Auth管理APIの`deleteUser(id, false)`でハード削除する。管理キーの利用用途が退会にも拡張される。通常のユーザー権限で任意ユーザーを削除するRPCは追加しない。緊急停止modeがnone以外なら退会を拒否する。

既存外部キーのON DELETE CASCADEによりプロフィール・画像・学習記録/メモ・投稿/返信・リアクション・フォロー/ブロック・DM申請・送受信DM・個人別の認証復旧データ等を削除する。本人の投稿に付いた他人の返信も投稿とともに消え、DMは相手側の会話からも消える。無関係な利用者の投稿は残る。既存の権限関数は削除済みアカウントを拒否するため、期限内の古いJWTによるアプリDB操作も拒否される。

成功時にブラウザのアプリCookieを削除しトップへ戻す。物理削除なのでユーザーの通常操作で復元できない。Cookie削除の失敗や通信切断など、削除済みでも成功応答が届かない場合があり、その場合は再ログインで状態確認を案内する。

バックアップ・クラウドの運用ログ・メール・他人が保存したスクリーンショットの即時消去は対象外。サービスごとの保存期間と削除運用は別途確定・開示が必要。個人識別情報を含まない監視集計は保持する。Storage機能を追加する場合はAuth削除を妨げる所有オブジェクト等への対応を別途実装する。

検証：隔離DBでAuth削除の連鎖・送受信DM削除・第三者投稿維持・削除済みIDでの取得拒否を確認。別ID偽装・確認文字欠落・誤パスワード・MFA欠落/誤コード拒否と正常系を試験。実ユーザーは削除していない。本番への反映・専用使い捨てアカウントの退会・実サービスのセッション挙動確認は別途必要。

今回の確認結果：単体・隔離DB計48テスト成功、HTTP試験1件成功、production build・TypeScript検査成功。HTTPでは退会APIの未認証401、不正Origin/CSRF400を確認した。試験サーバーはダミー接続先を使用し、本番のアカウント削除は行っていない。
