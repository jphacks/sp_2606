# 秘密情報の検知・漏洩対応

## 実装範囲

GitHubのSecret scanが、mainへのpush・PR・週次・手動実行で履歴を検査する。検知したらジョブを失敗にし、鍵の値・ファイル名・ソース断片を含まない件数と暫定分類だけを表示する。main・定期・手動の検査で検知またはスキャナーが失敗した場合、GitHub Actionsが運営者ryo7-7に担当を割り当てたIssueを作成する。同じ対応Issueが開いていれば追記する。PRからはIssue作成用権限を使わず、チェック失敗で知らせる。

通知メールの到達はGitHubアカウントの通知設定に依存する。GitHubのNotificationsでAssignment通知とメール設定を確認する。Issue無効・権限不足・API障害なら通知ジョブも失敗するため、Actions失敗通知も有効にする。常時監視や通知の確実な到達を保証するものではない。

本番の秘密はGitHubに登録しない。検出した値を外部APIへ送り、有効性を確かめる処理も行わない。分類はキー形式と検出ルールに基づく候補で、使用中の本物の鍵かは断定しない。Supabase管理キー・Gmailアプリパスワードの自動発行／失効はしない。

## 検知したら

1. Issue内のActionsリンクを開く。`other`は不明であり、安全という意味ではない。スキャナー失敗は「問題なし」ではない。
2. 元のGit履歴・設定は運営の端末で調べる。鍵をチャット、Issue、スクリーンショットへ貼らない。必要なら技術担当に「種類・場所・検査結果」だけを渡して対処を判断してもらう。
3. 本物の鍵が公開されていたら、悪用の証拠を待たず失効・交換する。現在の鍵と一致しない場合も、過去の有効な鍵かもしれないため、誤検知として自動除外しない。
4. 次の表から停止範囲を選ぶ。判断がつかなければ運営が全体停止し、専門担当と原因を確認する。

| 種類 | 最初の停止設定 | 交換・失効先 |
|---|---|---|
| 復旧用Supabase Secret | `COSTEP_INCIDENT_MODE=recovery`。範囲不明ならall | Supabaseで該当Secretを失効。必要な新規キーを発行しVercelのProductionサーバー環境変数へ設定 |
| 復旧メールSMTPパスワード | `COSTEP_INCIDENT_MODE=recovery` | Googleの該当アプリパスワードを削除して失効。新しく発行し復旧用Vercel環境変数を更新 |
| Supabase Auth自身のSMTPパスワード | 必要に応じ全体停止 | Supabase AuthのSMTP設定も更新。復旧用SMTPと同じ鍵なら両方を更新。復旧停止フラグだけではAuthサービスの送信を止めない |
| セッション暗号鍵 | `COSTEP_INCIDENT_MODE=all` | 新しい32バイト乱数を生成し`SESSION_ENCRYPTION_KEY`を置換。旧鍵を復号の予備として残さない |
| その他・範囲不明 | `COSTEP_INCIDENT_MODE=all` | 該当サービスで鍵を特定し失効。公開用Supabaseキーは公開前提なので秘密キーと区別する |

**アプリ停止はSupabaseへの直接アクセスを止めない。特に漏れた管理キーはRLSを迂回できるため、サービス側の失効が必須。**

## 停止の実行

Vercelのstudy-circle Production環境変数に設定し、再デプロイする。

- `none`（既定）：通常稼働。
- `recovery`：MFAメール復旧と専用の管理クライアント／復旧メール送信を停止。通常のタイムラインと認証アプリは継続。
- `all`：アプリのページ・API・認証コールバックを503、no-storeで返す。アクセスしたブラウザのアプリCookieを削除。不正な設定値もallとして扱う。

静的JS等は引き続き配信される。開いている画面の既取得情報を遠隔消去することはできない。環境変数変更だけでは既存デプロイに反映されない。過去のVercelデプロイURLも影響確認の対象とし、古い鍵のサービス側失効を優先する。

ローカルの設定確認：`npm run incident:status`。秘密値は出力しない。これは本番Vercelへ反映された証明ではない。

## セッション鍵交換と再ログイン

1. 全体停止した上で、新しい暗号学的乱数32バイトを運営の端末／パスワード管理ツールで生成し、安全に保管する。鍵を標準ログや公開ファイルに残さない。
2. Vercel Productionの`SESSION_ENCRYPTION_KEY`を新しい値に置き換える。対応するローカル設定も更新。GitHub ActionsのSecretには入れない。
3. `SESSION_NOT_BEFORE`に対応開始のUTC日時を設定できる（例：`2026-10-18T06:00:00Z`）。それより前に作成されたアプリセッションを拒否し、更新しても元の作成日時を維持する。無効な日時はセッションを拒否する。
4. 再デプロイ後、旧Cookieが使えないことを確認する。暗号鍵の交換は既存のパスワード復旧証明、MFA復旧Cookie、PKCEの暗号情報も無効にする。利用者は再ログインやメール再送が必要。
5. 暗号鍵が漏れた際にCookieも取得された可能性があれば、Supabaseの該当ユーザーのセッション・トークン失効も行う。**暗号鍵交換と日時制限だけでは、既に盗まれたSupabase access/refresh tokenを失効できない。** Access tokenの失効時期・JWT有効期間は別に確認する。日時制限だけで暗号鍵交換を省略しない。

## 再開前に確認すること

- 旧Supabase Secretでの管理API要求が拒否されること。旧SMTPアプリパスワードで送信認証できないこと。値をログに残さず確認する。
- Vercelが新しい設定でデプロイ済みであること。過去デプロイを含め旧キーを使う経路を確認する。
- 別ブラウザの古いアプリCookieでアクセスできず、新規ログインができること。
- メール復旧を再開する場合、新しい鍵で実際に復旧メールが届くこと。
- `npm run test:ci`、型チェック、ビルドとHTTP保護試験が通ること。
- 被害範囲・日時・失効対象・利用者連絡の要否を記録する。記録に秘密そのものを残さない。
- 確認後`COSTEP_INCIDENT_MODE=none`で再デプロイし、通常利用を確認する。

対応Issueは解決確認後に閉じる。検出した記述を消すだけで完了にしない。

## 今回の検証と未実施事項

分類に秘密文字列を混ぜても通知用出力に含まれないこと、停止時の503/no-store/Cookie削除、復旧停止設定、セッション作成日時制限を自動テストする。通知APIは模擬応答で検証し、本物の鍵・本番利用者の設定・Google/Supabaseの鍵を失効させる訓練は行わない。

このファイルの実装完了だけで、通知メールの実配送や本番の停止・再開・鍵交換の実地確認まで完了したことにはしない。
